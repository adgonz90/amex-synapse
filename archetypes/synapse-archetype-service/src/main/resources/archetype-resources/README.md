# ${rootArtifactId}

The `${serviceName}` service, a Synapse 2 service generated by `synapse-archetype-service`: items served over REST and
gRPC from one set of operations, on PostgreSQL. It is laid out as the
[`reference-bookstore`](https://github.com/americanexpress/synapse/blob/main/samples/reference-bookstore/README.md)
sample, with one aggregate, `Item`, and two operations, create and get: a contract module with what callers depend
on, a data module that owns the `${serviceName}` store, and a bootable service module with the operations and their
two bindings. Both protocols take the same requests and give the same answers, codes and entity tags. Run it, then
make it yours.

It uses `synapse-api-rest`, `synapse-api-rest-openapi`, `synapse-api-grpc`, `synapse-data-jpa`,
`synapse-data-postgres`, `synapse-logging-log4j2` and the Synapse test modules. The bookstore sample shows what the
next operations look like: search with page tokens shared by both protocols, and updates and deletes with a required
version (`If-Match` over REST, the `etag` field over gRPC).

#[[## What it shows]]#

Code paths are under `contract-${serviceName}/src/main/`, `data-${serviceName}/src/main/` and
`service-${serviceName}/src/main/java/${packageInPathFormat}/`.

| Feature | Where |
|---|---|
| A contract module: the records the operations take and return, the error codes (`ITEM_NOT_FOUND`) and the `.proto`, from which the gRPC classes are generated | `contract-${serviceName}/` |
| A data module that owns its store: `@SynapseDataStore("${serviceName}")` on JPA, the entity on `AuditedEntity`, the repository, the Flyway migration and the store's settings for every environment, shipped in its jar | `data-${serviceName}/` |
| Two operations (create, get) that know nothing of either protocol | `operation/` |
| One `RestBindings` bean and one `GrpcBindings` bean over the same operations, with the same declarations: the not-found code and the entity tag | `api/rest/ItemRestConfiguration.java`, `api/grpc/ItemGrpcConfiguration.java` |
| Readiness at `/health` that the store takes part in, and gRPC health | `application.yaml`, data-${serviceName}'s `config.yaml` |
| The OpenAPI document, gRPC reflection and CORS for a local front end, on in `local` only | `application-local.yaml` |
| Environments: `local` on `docker compose`, `test`, `build` (an image's training run and `-Paot`) and `dev`, an example of a deployed one | [Environments](#environments) |
| A container image from the `Dockerfile` or `-Pimage`, each with the JVM's AOT cache from a training run in `build`; Spring AOT with `-Paot` | [Spring AOT and container images](#spring-aot-and-container-images) |
| The OpenTelemetry Java agent as an alternative to Boot's own SDK: one configuration class, the agent jar from Maven with its checksum, and a test that runs the jar under it | [OpenTelemetry Java agent](#opentelemetry-java-agent) |
| One scenario suite that runs every case over both protocols and expects the same outcome, against the test context and, with `-Paot`, against the packaged jar in AOT mode | [Tests](#tests) |

The packages follow Synapse's layering: `api.rest` and `api.grpc` call `operation`, which calls
`data.${serviceName}`; every layer may use `contract`, and nothing calls `api`. The data module's package is under the
service's root package, so the service's component scan finds the store, and `ArchitectureTest` checks it as the
`data` layer. The entity is `StoredItem`, and the operations return the record `contract.Item`: an operation's input
or output is never a persistence entity, so the operations map one to the other (`operation/ItemMapping.java`).

#[[## Environments]]#

The environment is the one active Spring profile: `application.yaml` maps `spring.profiles.active: ${ENV}`, so the
platform sets `ENV`, and the service doesn't start without it. Each environment has a file in the service and may have
one in the data module:

| Environment | Service file | data-${serviceName} file | What it is |
|---|---|---|---|
| `local` | `application-local.yaml` | `config-local.yaml` | Your machine, with the database of `compose.yaml`. Turns on problem detail, gRPC reflection, the OpenAPI document, CORS for `http://localhost:3000` and the health components |
| `test` | `src/test/resources/application-test.yaml` | none | The tests. Problem detail is on for the slice tests; the integration tests turn it off again and connect the store to a container |
| `build` | `application-build.yaml` | `config-build.yaml` | An image's AOT-cache training run, and `process-aot` with `-Paot`. Sets nothing, so the build-time switches keep their defaults (off); the store points at a closed port |
| `dev` | `application-dev.yaml` | `config-dev.yaml` | An example of a deployed environment. Changes nothing but where the store connects; the user name and password come from `SYNAPSE_DATA_STORES_${serviceName.toUpperCase()}_USERNAME` and `SYNAPSE_DATA_STORES_${serviceName.toUpperCase()}_PASSWORD` |

Every safety setting keeps its safe default in every environment, and only an environment's file turns a convenience
on. The user name and password in `config-local.yaml` are those of the throwaway compose container, marked *local
compose only*; no other file holds a credential.

#[[## Run it]]#

You need JDK 21 or later, and Docker for the database and the integration tests. The project has the Maven Wrapper,
so every build uses the same Maven: the wrapper downloads Maven 3.9.16 the first time it runs. The commands are for Git
Bash on Windows or any POSIX shell; in PowerShell or cmd, `.\mvnw.cmd` takes the place of `./mvnw` (and `..\mvnw.cmd`
of `../mvnw`). If you commit the project from Windows, run `git update-index --chmod=+x mvnw` after `git add`, so
that `mvnw` is executable where the repository is checked out on Linux (CI, a container build). On Windows without
long paths (`LongPathsEnabled`), keep the path of this directory under about 75 characters, less the length of the
service name: the deepest file the build writes, under `contract-*/target` (the protobuf plugin's extracted imports),
is 184 characters below it with a one-letter name. With `-Paot` it is 232
(Spring's generated classes under `service-*/target/spring-aot`), which leaves about 27 characters, less the length of
the service name (20 for `example`): few directories are that short, so enable long paths for
`-Paot`. Maven and the JVM cope with longer paths; other tools that read `target/` may not.

From this directory, start the database (`down -v` first removes one left from an earlier run), then build the service
and run it:

```bash
docker compose down -v
docker compose up -d
./mvnw package -DskipTests
ENV=local java -jar service-${serviceName}/target/service-${serviceName}-${version}.jar
```

`./mvnw package` builds the three modules without running the tests (`./mvnw verify` runs them; see [Tests](#tests)).
The last command runs the `local` environment. `./mvnw install -DskipTests`, then `../mvnw spring-boot:run` in
`service-${serviceName}`, runs it too (the pom sets `spring-boot.run.profiles=local`).

The service listens on port 8080 (REST) and 9090 (gRPC) and logs ECS JSON, one object per line. These are the lines
that matter (the `@timestamp`, `process` and `service` fields are left out here). The store starts its pool and runs

`/health` is the readiness group (`additional-path: server:/health` in `application.yaml`): Boot's `readinessState`
and the `${serviceName}` store, which opts in with `health.readiness: true` in data-${serviceName}'s `config.yaml`, so
while the database is down the service answers 503 and the platform stops sending it traffic. Configuring the
readiness group defines it, and a group includes every indicator unless it lists its members, so when an application
configures the group, as `application.yaml` does with `additional-path`, Synapse defaults its `include` to
`readinessState` (an `include` of yours replaces it; without a key of the group, Boot's probe group keeps its
settings, and the stores that opt in still join it) and adds the stores that opt in.

The scenarios are in `scenario/ItemScenarios`: each runs over both protocols, with `RestItemClient` (the JDK's HTTP
client) and `GrpcItemClient` (the generated stub), and compares one `Outcome` (kind, error code and category, item,
entity tag). Each client also checks its own protocol's statuses. A subclass says where the service runs:
`ServiceJvmIT` the test context, `ServiceAotIT` the packaged jar, which `scenario/AppProcess` starts as its own
process, on free ports, waits for `/health`, and stops.

```bash
./mvnw verify
./mvnw -Paot verify
```

run them (`*Test` in the `test` phase, `*IT` in `verify`; the integration tests need Docker). The first leaves out
`ServiceAotIT`, which needs the AOT-generated code; the second runs AOT processing and every test. The generated code


#[[## Spring AOT and container images]]#

Both need the build environment's files, `service-${serviceName}/src/main/resources/application-build.yaml` and
data-${serviceName}'s `config-build.yaml`, which this project has (comments, and a store url on a closed port).

* **Spring AOT** is opt-in, with `synapse-parent`'s `aot` profile: `./mvnw -Paot package` runs `process-aot` in
  the build environment and puts the generated code in the jar; `java -Dspring.aot.enabled=true -jar ...` runs it.
  What the build decided can't change at run time: the build keeps the OpenAPI document and gRPC reflection off, so
  the AOT-processed jar runs in `dev`, but a run in `local`, which turns both on, fails at startup naming both.
  `./mvnw -Paot verify` checks both with `ServiceAotIT`.
* **A container image** with the `Dockerfile`, on a digest-pinned Temurin 25.0.5+8 JRE:

  ```bash
  ./mvnw clean package -DskipTests
  docker build -t ${serviceName}:dockerfile service-${serviceName}
  ```

  Its training run starts the jar in `build`, records the classes it loads into an AOT cache (JEP 483) and exits once
  the context has refreshed, with no database to reach; `ServiceExitOnRefreshIT` checks that run in every build. The
  collector is pinned to G1 in the training run and in every run, so a small pod still loads the cache.
* **Or with Paketo**: `./mvnw -Pimage clean package` builds the image `service-${serviceName}:${version}`
  with `synapse-parent`'s buildpack settings, with the same training run. The `image` profile first checks for
  `application-build.yaml` and fails in `validate` without it. Keep one way to build the image.

Run either image in `dev`, with the store's connection from the variables a platform sets:
`SYNAPSE_DATA_STORES_${serviceName.toUpperCase()}_URL`, `_USERNAME` and `_PASSWORD`. The details are in the
[parent POM documentation](https://github.com/americanexpress/synapse/blob/main/docs/modules/ROOT/pages/parent.adoc)
(*Build environment* and *Images*) and the bookstore's README (*AOT mode*, *Container image*).

#[[## OpenTelemetry Java agent]]#

The service traces with Boot's OpenTelemetry SDK. To trace with the OpenTelemetry Java agent instead, start the jar
with `-javaagent:`; `config/OpenTelemetryAgentConfiguration` then hands Boot's bridge the agent's SDK, so Boot's
observations, Synapse's baggage and the agent's instrumentation share one SDK and one trace. Without the agent the
class does nothing. In AOT mode the condition was fixed at build time, without the agent, so
`config/OpenTelemetryAgentAotConfiguration` fails such a start under the agent and says what to do.

The build copies the agent jar (2.33.1) to `service-${serviceName}/target/otel` before the tests are compiled, and fails
unless it has the SHA-256 pinned in the pom (`opentelemetry-javaagent.sha256`):

```bash
ENV=local java -javaagent:service-${serviceName}/target/otel/opentelemetry-javaagent.jar \
  -Dotel.service.name=${serviceName} -Dotel.traces.exporter=logging -Dotel.metrics.exporter=none -Dotel.logs.exporter=none \
  -jar service-${serviceName}/target/service-${serviceName}-${version}.jar
```

`../mvnw spring-boot:run -Potel-agent` in `service-${serviceName}` does the same with every exporter off.
`ServiceAgentIT` runs the jar under the agent in every build, so an upgrade of Synapse or of the agent that breaks the
recipe fails the build, not a deployment. The recipe is in
[`opentelemetry-agent.adoc`](https://github.com/americanexpress/synapse/blob/main/docs/modules/ROOT/pages/opentelemetry-agent.adoc).

#[[## Make it yours]]#

* Rename `Item` to your aggregate: the records and `ItemErrors` in the contract, the messages and `ItemService` in
  `${serviceName}.proto`, `StoredItem`, `ItemRepository` and the table in V1, the operations, the bindings and the
  tests. Add operations one at a time, each with its tests and its scenarios; the bookstore shows search, update and
  delete.
* Rename `ServiceApplication` and `ServiceStore` if you like; `ArchitectureTest` names the application class.
* Migrations are append-only: add `V2__...sql` next to `V1__${serviceName}.sql`, never edit one that has run.
* data-${serviceName}'s `config-<env>.yaml`, one per environment you deploy to, with the `url` only, and
  `application-<env>.yaml` for each, never turning on a build-time switch that the build leaves off.
* The build environment's files, `application-build.yaml` and data-${serviceName}'s `config-build.yaml`, exist for the
  image's training run and for `-Paot`. If you build neither an image nor with `-Paot`, delete them with the
  `Dockerfile`, `.dockerignore`, `ServiceExitOnRefreshIT`, `ServiceAotIT` and the `aot` profile of
  `service-${serviceName}/pom.xml`.
* If you don't run the OpenTelemetry Java agent, delete `config/OpenTelemetryAgentConfiguration`,
  `config/OpenTelemetryAgentAotConfiguration` and their test, `ServiceAgentIT` and `ServiceAotIT`'s
  `aotRunUnderTheAgentFailsFast`, `AppProcess.agentJar()`, the `otel-agent` and `otel-agent-checksum` executions, the
  `otel-agent` profile, failsafe's `service.otel-agent` property, and the three `opentelemetry-javaagent`/`otel-agent`
  properties in `service-${serviceName}/pom.xml`.
* When you upgrade Synapse, check its `SynapseContainers.POSTGRES_IMAGE` and update `compose.yaml`'s digest to match.
* The poms' `description`s; deploy the contract module, so that callers can depend on it.
* The license header at the top of each file is the one of Synapse's own sources: put your own in its place.
