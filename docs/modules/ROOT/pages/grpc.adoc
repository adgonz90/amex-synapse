= gRPC

`synapse-api-grpc` exposes operations as gRPC services on Spring Boot's gRPC server. You bind the methods of a
service generated by `protoc` in a `GrpcBindings` bean; Synapse compiles it into a service that Boot serves, maps each
request message to the operation's input record, calls the operation through the pipeline and maps its output to the
response message. Errors are gRPC statuses with `google.rpc` error details.

[source,xml]
----
<dependency>
  <groupId>io.americanexpress.synapse</groupId>
  <artifactId>synapse-api-grpc</artifactId>
</dependency>
----

The module brings Boot's gRPC server module (`spring-boot-grpc-server`, not the starter, which would add a logging
backend), `grpc-netty`, `grpc-services` (reflection and health), `grpc-protobuf` and `grpc-stub`. The service module
also generates its messages and stubs from its `.proto` files, for example with the `protobuf-maven-plugin` that
`spring-boot-starter-parent` configures.

* *Transport.* Boot runs a Netty server on `spring.grpc.server.port` (9090 by default), next to the web server if
  there is one. To use shaded Netty, exclude `io.grpc:grpc-netty` from `synapse-api-grpc` and add
  `io.grpc:grpc-netty-shaded`, as Boot documents.
* *Servlet transport.* gRPC served by the servlet container (a `GrpcServletRegistration` bean) is not supported
  together with `synapse-api-rest`: the REST edge filters would apply to gRPC calls. Startup fails with
  `gRPC served by the servlet container is not supported together with synapse-api-rest yet: the REST edge would filter
  gRPC calls.` (action: `Use the default Netty transport (keep io.grpc:grpc-netty), or remove synapse-api-rest.`).

The plugin is active when Spring gRPC and grpc-java are on the class path and `spring.grpc.server.enabled` is not
`false`. Boot starts its server only when at least one service bean exists. As with every operation, tracing must be
present (see xref:core.adoc#tracing[Tracing is required]). An operation bean and a `GrpcBindings` bean are all the
configuration a method needs.

NOTE: Not available yet: streaming methods, input components bound from request metadata, and gRPC clients (P2).

The sample `samples/grpc-inventory` in the repository is a gRPC service with its `.proto` in a contract module, and
uses most of this page: every field kind, a `oneof`, a renamed field, entity tags, page tokens, context metadata and
a per-operation status override. Its
https://github.com/americanexpress/synapse/blob/main/samples/grpc-inventory/README.md[README] calls it with
`grpcurl`.

== Bindings

[source,java]
----
@Bean
GrpcBindings bookService(GetBookOperation getBook, CreateBookOperation createBook) {
    return GrpcBindings.service(BookServiceGrpc.getServiceDescriptor())
        .unary(BookServiceGrpc.getGetBookMethod(), getBook).notFound(BookErrors.BOOK_NOT_FOUND)
            .etag(Book::version)
        .unary(BookServiceGrpc.getCreateBookMethod(), createBook)
            .context(CreateBookRequest::channel, context -> context.attribute("channel").orElse(null))
            .etag(Book::version)
        .bindAllByName()
        .build();
}
----

* One `GrpcBindings` bean binds one service. Declare one bean per service.
* `.unary(method, operation)` binds a method, given by its generated descriptor, to an operation bean. Only
  `QueryOperation` and `CommandOperation` beans can be bound; a `BusinessOperation` does not compile.
* `.bindAllByName()` binds each method that no `.unary` call binds to the operation named after it: `GetBook` to
  `get-book`, `GetHTTPStatus` to `get-http-status` (see xref:core.adoc#_contracts_and_naming[Contracts and naming]).
* Per method: `.map("field.path", Record::component)` binds a component to another field, `.context(Record::component,
  ctx -> ...)` sets an input component from the request context instead of a field, `.notFound(code)` sets the
  error of an empty `Optional` (see <<not-found>>), `.etag(Record::component)` sends an output component as the
  response's entity tag (see <<versions>>), and `.sortable(SortKey.class)` lists the keys a page may be sorted by (see
  <<paging>>).

Components are referenced by method reference, never by string, so renaming a record component breaks the
compilation of the binding, not startup. Bindings belong in the service module's `api.grpc` package. The bean is a
`BindableService`, so Boot's server serves it like a hand-written service and applies the same interceptors.

Building the bindings only records them. They are checked and compiled when the bean is created, so the bean must be
declared with `@Bean`: a `GrpcBindings` that Synapse never compiled throws
`GrpcBindings for <service> was not compiled: declare it as a @Bean so synapse-api-grpc can bind it` when the server
asks for it. Every method of the service must be bound, so a service with a streaming method is written by hand (see
<<escape-hatch>>).

The operation must be the Synapse bean, so that its calls run through the pipeline (validation, deadline,
observation, translation and failure logging).

Startup also fails, with the method named, when:

* the input type is not a record, a `PageQuery` or `Void`, or the output is not a record, an `Optional` or `List` of
  one, a `PageResult` or `Void`;
* a `PageQuery` is inside another type of the input (not the input or a component of the input record itself), the
  input has two, a `.map` or `.context` names one, or one is in the output; a `PageResult` is in the input, or
  anywhere in the output but the output itself (an `Optional<PageResult<...>>`, a page of pages);
* `.sortable` is declared twice, or with an enum without constants, with a constant whose lower-case name is not made
  of `a-z`, `0-9` and `_`, or with two constants whose names are the same in
  lower case;
* on a method that binds a `PageQuery` or returns a `PageResult`, an input component can't be put into the cursor's
  digest (`<record>.<component> (type <type>) can't be bound into a paging cursor; use a record or simple type`; see
  <<paging>>);
* the input or output is nested more than 32 levels deep or holds more than 10,000 types;
* a `.map` component is in neither the input nor the output record (or a record nested in one), a `.map` path names
  no field, or a `.context` component is not in the input;
* a component has two sources (`.map` and `.context`, or two of either);
* `.notFound` is declared on a method whose output is not an `Optional`;
* two output components write the same field (or one writes inside the other's message), or write members of one
  `oneof` and one of them is not `@Nullable` (see <<mapping>>);
* a Java enum constant has no protobuf value, or matches the enum's unspecified value (see <<mapping>>);
* a `VersionCondition` has no concrete version type (raw, `VersionCondition<?>`, `VersionCondition<Object>`), or
  appears in the output;
* `.etag` is declared twice, on an output that is not a record or an `Optional` of one, for a component of the output
  record whose type is not a version type (the same set as REST: a string, an integral number or a `java.time` value;
  not a boolean, an enum, a floating-point number or a `UUID`), or where another component also writes the response's
  `etag` field (see <<versions>>).

[#mapping]
== Message mapping

Synapse reads the request and writes the response as `DynamicMessage`s over the generated descriptors; it never
instantiates the generated message classes. A component maps to the field whose JSON name equals the component name
(`published_on` and `publishedOn`). `.map("author.name", Record::component)` names another field: the path is
relative to the message of the component's own record, dotted to reach a field of a nested message.

[cols="2,3",options="header"]
|===
|Proto field |Record component
|`string` |`String`, or any type Boot's `ApplicationConversionService` converts both ways (`UUID`, `BigDecimal`,
`LocalDate`). `java.time` values are read and written in ISO only, whatever the locale.
|`int32`, `sint32`, `sfixed32`, `uint32`, `fixed32` |`int`/`Integer` or `long`/`Long`
|`int64`, `sint64`, `sfixed64`, `uint64`, `fixed64` |`long`/`Long`
|`bool`, `double`, `float` |Their Java types
|`bytes` |`byte[]`
|`google.protobuf.Timestamp` |`Instant`, from 0001-01-01T00:00:00Z to 9999-12-31T23:59:59.999999999Z
|`google.protobuf.Duration` |`java.time.Duration`
|The nine wrapper types (`Int32Value`, `StringValue`, ...) |A component of the wrapped type, usually `@Nullable`
|An enum |A Java enum (see below)
|Another message |A record
|`repeated T` |`List<T>`
|`map<K, V>` |`Map<K, V>`
|===

Enums match by name: a value matches the constant of the same name, or the constant named by the rest of the value
after the enum's prefix, as the protobuf style guide names values (`GENRE_FICTION` in `enum Genre` is
`Genre.FICTION`). A zero value named `*_UNSPECIFIED` or `*_UNKNOWN` is `null`. Every Java constant needs a value.

*Presence.* A `@Nullable` component needs a field with presence: a message, a wrapper, a proto3 `optional` field, a
`oneof` member, or an enum whose zero value is unspecified. Otherwise "absent" would silently become `0` or `""`, and
startup fails. A field without presence always has a value (its default), so a non-null component bound to one is
never missing.

*`oneof`.* A `oneof` member is mapped only with an explicit `.map`. The synthetic `oneof` of a proto3 `optional` field
doesn't count. Map each member you use to its own `@Nullable` component, on the request and on the response, and
make the record allow at most one of them in its constructor:

[source,java]
----
// message Item { string id = 1; oneof price { Money fixed = 2; Discount discounted = 3; } }
record Item(String id, @Nullable Money fixedPrice, @Nullable Discount discountedPrice) {
    Item {
        if (fixedPrice != null && discountedPrice != null) {
            throw new IllegalArgumentException("An item has a fixed or a discounted price, not both");
        }
    }
}

.unary(InventoryServiceGrpc.getGetItemMethod(), getItem)
    .map("fixed", Item::fixedPrice)
    .map("discounted", Item::discountedPrice)
----

*Why the record checks itself.* A `oneof` is part of the contract: a value has at most one of its members, whatever
the protocol. A record of two `@Nullable` components doesn't say that on its own. Over REST, it would be written as
two properties and accepted from a body that carries both, while over gRPC a request can't carry both and a response
can't hold both. The constructor check makes the record say it, so both protocols accept and return the same values:
a REST body with both is `VALIDATION_FAILED` (a constructor that throws, see xref:rest.adoc[REST]), and no operation
can return a record with both. Synapse's own check on the gRPC response, below, is only the backstop for a record
that doesn't check itself.

* *Request.* The component of the member the caller set gets its value; the others are `null`. With no member set,
  all are `null`.
* *Response.* The component that has a value sets its member; when all are `null`, the `oneof` is unset. Setting a
  second member would silently clear the first, so a record with more than one of them set fails the call with
  `INTERNAL` (no detail reaches the caller), and the ERROR log names the method, the `oneof` and the components:
  `gRPC method <service>/<method> (<operation>): Item.fixedPrice and Item.discountedPrice both have a value, but they
  write members of oneof <message>.price, which holds one`. This is the backstop: with the constructor check above it
  can't happen.
* Every component that writes a member of a shared `oneof` must be `@Nullable`; a non-null one would always clear the
  others, so startup fails: `<record>.<component> and <record>.<component> both write oneof <message>.<oneof>, and
  <record>.<component> is not @Nullable` (action: `Declare each component that writes a member of the oneof @Nullable,
  so that at most one has a value, or map only one component to the oneof.`). A single component mapped to one member
  may be non-null.

A component that writes a field inside a member (`.map("fixed.amount", ...)`) counts as writing that member.

*Shapes.*

* A `Void` input takes `google.protobuf.Empty` or any message without fields.
* A `Void` output, or a `null` one, writes the empty response message.
* An `Optional<T>` output writes its value; an empty one is the method's not-found error (see <<not-found>>).
* A `List<T>` output writes the response message's only field, which must be `repeated`.
* A `PageQuery` input or component reads the request's AIP-158 page fields, and a `PageResult<T>` output writes an
  AIP-158 page (see <<paging>>).

*Input.* Request fields without a component are ignored. Every input component needs a field or a `.context`. Problems
are collected, in component order, into one `VALIDATION_FAILED` (`INVALID_ARGUMENT`) with a violation per field, at
most 50:

[cols="3,2",options="header"]
|===
|Problem |Violation message
|A value that can't be converted (an id that isn't a UUID, an unknown enum number, a date that isn't ISO, an unsigned
value too large for the component) |`is not a valid value`
|A non-null component whose field is absent (a message, wrapper or `optional` field not set, an unspecified enum)
|`must not be null`
|An `etag` that isn't an entity tag list (see <<versions>>) |`must be an entity tag`
|An `etag` with more than one tag |`must be a single entity tag`
|===

The violation `field` is the proto field path from the request (`author.country_code`, `tags[2]`); in a map, it is
the map field's path, because the key is the caller's data. A component set by `.context` is named by its component
name. Violations never repeat the rejected value. The record is built with its canonical constructor once every field
is read. A constructor that throws is `VALIDATION_FAILED` without violations for the request's own record, and
`{field, is not a valid value}` for a nested record (the exception is logged at DEBUG); a `SynapseException` it throws
reaches the caller unchanged. Jakarta Validation then runs in the pipeline, and its violations are named by the proto
field path too (`published_on`), or by the component path when the binding maps no field to it. Inside a list the
names are the proto ones and the index is kept (`authors[0].country_code`). Inside a map the key is left out, as the
request's own violations leave it out (`authors_by_rank.country_code`), so a field has one name and the caller's key
is never echoed. A path that names a list or map element but can't be read against the binding is cut before its
first bracket.

*Output.* Every output component needs a field; response fields without a component stay unset, and a `null`
component leaves its field unset. A value that can't be written (outside its field's range, a `null` list element, or
two members of one `oneof`) fails the call with `INTERNAL`, logged at ERROR with the method and the operation.

[#versions]
== Versions and entity tags

A version travels over gRPC as the same token as over REST, so a client can take an `ETag` from a REST response and
send it over gRPC, and the reverse. Following AIP-154, the token is a `string etag` field of the message:

[source,protobuf]
----
message Book {
  string id = 1;
  int64 version = 7;
  string etag = 8;      // the strong entity tag "7", filled by .etag(Book::version)
}

message DeleteBookRequest {
  string id = 1;
  string etag = 3;      // "7", or *: what If-Match carries over REST
}
----

*Two token fields, REST's two headers.* A request carries an entity tag in one of two fixed string fields, each with
its REST header's rules:

[cols="1,1,3",options="header"]
|===
|Field |REST header |Bound to a `VersionCondition` component by
|`etag` |`If-Match` |Default: a `VersionCondition` component binds from `etag` whatever it is called (`version` in
the record), or with `.map("etag", Record::component)`
|`if_none_match` |`If-None-Match` |`.map("if_none_match", Record::component)`, as REST's
`.header("If-None-Match", Record::component)`
|===

As REST binds at most one component from each header, an input has at most one `VersionCondition` per field. Each is
a component of the input record itself (not of a nested record or inside a container), and `.context` can't supply
one. A plain component can't be mapped to either field: its text is an entity tag, not a value.

*Request.* The value is the header value, copied verbatim: `"5"` with its double quotes, or `*`. It is parsed with the
same strict entity tag grammar as REST (RFC 9110), and the tag's value is read as a `V` version token, with the codec
REST uses (see xref:rest.adoc#version-tokens[version tokens]: plain decimal, ISO-8601, or the string itself, whatever
the locale). `"5"` is `Version(5L)` for a `VersionCondition<Long>`. On a write (a method bound to a
`CommandOperation`):

[cols="2,3,3",options="header"]
|===
|Value |`@Nullable VersionCondition<V>` (optional) |`VersionCondition<V>` (required)
|Empty (or an unset `optional string`) |`null` reaches the operation |`FAILED_PRECONDITION` with the code
`PRECONDITION_REQUIRED` (REST's 428), before the operation runs, with a violation that says how to resubmit (below)
|`*` |`AnyVersion` |`AnyVersion` (it satisfies "required")
|`"5"` |`Version(5)` |`Version(5)`
|A weak tag (`W/"5"`) in `etag`, which never matches under strong comparison |`FAILED_PRECONDITION` with
`PRECONDITION_FAILED` (REST's 412), before the operation runs |The same
|A weak tag in `if_none_match`, compared weakly |`Version(5)`, as REST binds a weak `If-None-Match` |The same
|Two tags, or a value off the grammar |`INVALID_ARGUMENT` with `VALIDATION_FAILED` |The same
|===

A missing required field gets REST's advice for its header: `{etag, is required; send the etag from a read of this
resource, or * for any current version}`, or `{if_none_match, is required; send * to write only if the resource
doesn't exist, or the etag the resource must not have}`; a request without either required field gets both.

Whether a `VersionCondition` is required is part of the operation's contract, not the binding's: a non-null component
is required over every protocol (see xref:core.adoc[Core]). `PRECONDITION_REQUIRED` gets `FAILED_PRECONDITION` from its
category, as REST's code gets 428; AIP-154 suggests `INVALID_ARGUMENT`, which
`synapse.api.grpc.errors.status.[PRECONDITION_REQUIRED]=INVALID_ARGUMENT` gives.

*Unbound tokens fail closed.* A write whose request sends a non-empty `etag` or `if_none_match` that no
`VersionCondition` binds is `FAILED_PRECONDITION` with `PRECONDITION_FAILED`, and the operation is not called, as REST
answers an `If-Match` or `If-None-Match` a `POST`, `PUT` or `DELETE` route doesn't bind with 412: the condition can't be
verified, and ignoring it would turn a conditional write into an unconditional one.

*Reads.* A method bound to a `QueryOperation` may bind a `@Nullable` `VersionCondition` from either field, as REST
binds one from `If-None-Match` on `GET`, and the operation decides what it means; a non-null one fails startup (a read
can't require a precondition). On a read, a weak tag binds its value and an unbound token is ignored, as REST checks
preconditions on writes only.

*Create-only writes*, as REST's `If-None-Match` on writes (see xref:rest.adoc[REST]): bind the condition from
`if_none_match`, and the operation reads `AnyVersion` (`*`) as "create only" and `Version(v)` as "unless it is at `v`",
throwing `PRECONDITION_FAILED` when the condition is false.

*Stale writes*, as over REST. The operation compares the version and writes with a compare-and-set, throwing
`STALE_VERSION` when either fails. When the request sent an `etag` (`*` included), that is a failed precondition:
`PRECONDITION_FAILED` (`FAILED_PRECONDITION`, REST's 412), with the `STALE_VERSION` as its cause. A write that sent no
`etag` and lost a race stays `STALE_VERSION` (`ABORTED`, REST's 409), and so does one that sent only an
`if_none_match`: REST's translation applies to `If-Match` only. AIP-154 answers a mismatch `ABORTED`;
`synapse.api.grpc.errors.status.[PRECONDITION_FAILED]=ABORTED` gives that, for weak tags too.

*Response.* `.etag(Record::component)` writes an output component as the strong entity tag (`7` becomes `"7"`) to the
response's `string etag` field, formatted as a version token, the same token REST sends as `ETag`; the component keeps
its own field too, and a `null` one leaves `etag` empty. The component's type is a version type (a string, an integral
number or a `java.time` value). As REST sends an `ETag` only on `GET`/`HEAD` and on the `201` of a `POST`, `.etag` is
allowed on a method bound to a `QueryOperation`, and on a `CommandOperation` whose input has no `VersionCondition` (a
create). An update or delete response carries no entity tag: read the resource again for the new one. A string an
entity tag can't carry (empty, or a double quote, a space, a control character, DEL or a character above U+00FF) fails
the call with `INTERNAL`. Both token fields must be singular `string` fields outside a `oneof` (a proto3 `optional` is
fine).

*Differences from REST*, each because of what HTTP has and gRPC doesn't:

* A read gets no 304. REST answers a `GET` whose `If-None-Match` matches its `ETag` with 304 Not Modified; gRPC has
  no such response, so the operation receives the condition (when it binds one) and the call answers normally.
* A plain (non-`VersionCondition`) component can't bind from `etag` or `if_none_match`. REST lets a read bind a plain
  `@Nullable` component from `If-None-Match`.
* `.context` can't supply a `VersionCondition` over gRPC; REST accepts `.context` and `.from` for one.

[#paging]
== Paging

A method pages when its operation takes a `PageQuery` and returns a `PageResult` (core's paging types, see
xref:core.adoc#paging[Paging]), the same operation REST pages. Following AIP-158, the request and the response carry
the page in fixed fields, and the response also says whether another page follows, as REST's `hasNext` does. Declare
the request's page fields `optional`, as the reference bookstore does: a value the caller sends then follows REST's
rules for its parameter (see *Unset* below):

[source,protobuf]
----
message SearchBooksRequest {
  string author = 1;                // a filter: SearchBooksRequest(@Nullable String author, PageQuery page)
  optional int32 page_size = 2;
  optional string page_token = 3;
  optional int32 skip = 4;          // the request message may omit this field
  optional string order_by = 5;     // needed with .sortable(...)
}

message SearchBooksResponse {
  repeated Book books = 1;  // the items, any name
  string next_page_token = 2;
  bool has_next = 3;        // REST's hasNext
  optional int64 total_size = 4;  // optional; int32 too
}
----

[source,java]
----
GrpcBindings.service(BookServiceGrpc.getServiceDescriptor())
    .unary(BookServiceGrpc.getSearchBooksMethod(), searchBooks).sortable(SearchBooksRequest.SortKey.class)
    ...
----

=== Request

`PageQuery` may be a component of the input record itself or the whole input (`QueryOperation<PageQuery,
PageResult<Book>>`), as over REST; an input has at most one. Its source is always the page fields: a `.map` or
`.context` for it fails startup, and so does another component of the input record that reads one of them.

[cols="1,2,4",options="header"]
|===
|Field |Required |Value
|`int32 page_size` |Yes |The page size: 1 to `synapse.paging.max-size` (100). Unset is
`synapse.paging.default-size` (20).
|`string page_token` |Yes |A `next_page_token` from a previous page, or a REST `nextCursor`. Unset is the first page.
|`int32 skip` |No |Items to skip: 0 to `synapse.paging.max-offset` (1000), inclusive. Unset is no offset.
|`string order_by` |With `.sortable` |Sort keys, AIP-132: separated by commas, each followed by `desc` to sort
descending (or `asc`), in lower case; U+0020 spaces around keys and words don't matter, and no other whitespace is
allowed: `"title, published_year desc"`. Unset is the operation's default order.
|===

Each field must be a singular field of its type outside a `oneof`. Startup fails when `page_size` or `page_token` is
missing, `order_by` is missing on a method with `.sortable`, or a page field has another type.

*Unset.* A proto3 `optional` field has presence: it is unset when the request doesn't send it, and a value it sends
follows REST's rules for its parameter (`page_size: 0` is a violation, `skip: 0` is offset 0). A plain field can't
tell its default from an unset field, so `page_size` 0, `skip` 0 and an empty `page_token` or `order_by` are unset.

The edge checks the fields before the operation runs, with core's caps, the same as REST's. Each problem is a
violation of the `VALIDATION_FAILED` (`INVALID_ARGUMENT`), with REST's message, named after the gRPC field where REST
names its query parameter, and the operation is not called:

[cols="2,3",options="header"]
|===
|Problem |Violation
|`page_size` below 1 (a plain field: below 0, as 0 is unset), `skip` below 0 |`must be greater than or equal to 1`
(or `0`)
|`page_size` above `synapse.paging.max-size`, `skip` above `synapse.paging.max-offset` |`must be less than or equal to
100` (the cap)
|`page_token` together with a sent `skip` |`{page_token, must not be combined with skip}`
|A sent empty `page_token` (an `optional` field) |`{page_token, is not a valid value}`
|A token the codec rejects |`{page_token, is not valid for this request}`
|A token that carries an offset above `synapse.paging.max-offset` (issued before the cap was lowered) |`{page_token,
must be less than or equal to 1000}` (the cap), as REST's `offset` over the cap
|`order_by` on a method without `.sortable` |`{order_by, is not supported}`, REST's text for `sort`
|A key `.sortable` doesn't allow |`{order_by, has a key that is not allowed (allowed: title, published_year)}`
|An empty key (`title,,author`), a key followed by a word other than `asc` or `desc` (`title DESC`), or whitespace
other than U+0020 (`title<TAB>desc`) |`{order_by, is not a valid value}`
|A key named twice |`{order_by, names a key more than once}`
|===

=== Sort keys

`.sortable(SortKey.class)` is the method's allow-list. A constant's `order_by` name is its name in lower case
(`PUBLISHED_YEAR` is `published_year`), the snake_case of AIP-132; `@JsonProperty` is not read, as gRPC has no JSON
names. The operation receives the constant's `name()` as `SortOrder.property()`, as over REST, so the same operation
code reads both protocols, and a cursor's scope is the same on both. Startup fails when `.sortable` is declared on a
method that doesn't bind `PageQuery`, is declared twice, names an enum without constants, has a constant whose
lower-case name is not made of `a-z`, `0-9` and `_` (`the sort key <Enum>.<CONSTANT> is not a valid order_by name: in
lower case, a constant's name must be made of letters, digits and '_'`), or has two constants with the same
lower-case name.

=== The page

A `PageResult` is written to the response's one repeated message field (any name, not a `map`; startup fails without
one, or with two), the token of the next page to `next_page_token`, its `hasNext` to `has_next`, and its total to
`total_size`, when the response has that field.

* `bool has_next` is required, beyond AIP-158 (which allows extra fields), because REST always writes `hasNext`. It is
  the page's own `hasNext`, also when no token reaches the next page (below). A proto3 `optional bool has_next` is
  accepted too; it is always written.
* `total_size` is `optional int32` or `optional int64`, so an unknown total stays unset. A total that an `int32` field
  can't hold is left unset, as an unknown one; declare `int64` for larger totals. A response without `total_size`
  doesn't carry the total.
* `PageResult` must be the operation's direct output, as over REST. The page's own fields, its raw cursor included,
  are never written as a message.

`next_page_token` follows REST's rule for `Link: next`:

* no token when the page has no next page (`hasNext` false), even if the operation returned a cursor;
* the operation's next cursor, wrapped, when it returned one;
* otherwise, when the request had no `page_token`, a token that carries the next offset (the request's `skip`, or 0,
  plus its size), so an operation that pages by offset only (`PageResult.of(items, hasNext)`, as
  `SpringDataPages.from(Page)` and `from(Slice)` return) pages through every item with tokens. The operation then
  receives `PageQuery(null, offset, size, sort)`;
* no token when the next offset would be past `synapse.paging.max-offset` (`has_next` is still true: page on by
  cursor), or when a page read by cursor returns no cursor.

=== Page tokens

`next_page_token` is a token of core's cursor codec, the one REST uses (xref:core.adoc#paging-cursors[Cursors]):
`synapse.paging.cursor.key`, its rotation and expiry apply to both protocols. A token carries a raw cursor or a next
offset, and is bound to the operation, the sort and a digest of the other input components; a gRPC method adds no
entries to the digest. So a token issued by an unversioned REST route pages over gRPC for the same operation, filters
and sort, and the reverse: REST's `cursor` parameter accepts an offset token too. A token for another operation, sort
or filters, a tampered or expired one, or one issued with another key is `{page_token, is not valid for this
request}`. The page size is not bound. The edge puts what the token carries into the input as REST does: it rebuilds
the input record with its canonical constructor. A token is unwrapped in REST's order: after the field violations and
a missing required `etag`, before a write's `etag` that can't be verified.

On a paged method, every input component but the `PageQuery` and the `VersionCondition`s must be one the digest can
write: REST's set (a string, number, boolean, enum, `java.time` value or `UUID`, a record of these, or a `List`, `Set`
or `Map` with `String` keys of them), plus `byte[]` and maps with non-string simple keys, which gRPC binds and REST
doesn't. A component set with `.context(...)` is digested too, so a token is bound to the caller when the caller is
part of the input. Any other type fails startup, so a garbage token is always `INVALID_ARGUMENT`.

Without `synapse.paging.cursor.key`, the key is generated at startup, and the first plugin with a paged route or
method logs one WARN, even when REST and gRPC both page (see xref:core.adoc#paging-cursors[Cursors]).

*Differences from REST*, each because of what AIP-158 and proto3 have and REST's query string doesn't:

* A plain (non-`optional`) field's default is unset: `page_size` 0 is the default size and a negative one is `must be
  greater than or equal to 0`, where REST rejects `size=0` (`... to 1`); `skip` 0 is no offset, so it combines with a
  `page_token`; an empty `page_token` or `order_by` is unset, where REST rejects an empty `cursor` or `sort`. Declare
  the fields `optional` to get REST's rules exactly.
* Sort keys are the lower-case constant names (`published_year`), where REST honours `@JsonProperty` and otherwise
  uses lowerCamel (`publishedYear`). The scope uses the constant names on both, so tokens are shared. AIP-132's
  spaces are insignificant in `order_by`; REST trims nothing in `sort`.
* There is no `Link` header: `next_page_token` carries what REST's `Link: next` carries (a cursor or a next offset),
  as a token, and REST's body `nextCursor` carries the same token (one rule in core, `PageCursors.next`).
* `total_size` is optional in the response, and an `int32` one leaves a total beyond its range unset; REST always
  writes `total` when the operation sets it.

[#errors]
== Errors

A failed call is a status code, a description, and a `google.rpc.Status` with error details (AIP-193) in the
`grpc-status-details-bin` trailer. With `synapse.errors.include-detail` on, a missing item of `samples/grpc-inventory`
reads, as grpcurl prints it:

----
ERROR:
  Code: NotFound
  Message: The resource was not found
  Details:
  1)	{
    	  "@type": "type.googleapis.com/google.rpc.ErrorInfo",
    	  "domain": "inventory",
    	  "metadata": {
    	    "correlationId": "demo-123"
    	  },
    	  "reason": "ITEM_NOT_FOUND"
    	}
----

grpcurl decodes the details only when it has their descriptors: the sample's `.proto` imports
`google/rpc/error_details.proto`, so server reflection serves them.

The details are, in this order:

* `ErrorInfo`, always: `reason` is the error code, `domain` is `spring.application.name` (or `synapse` when it is not
  set), and `metadata.correlationId` is the correlation id.
* `BadRequest`, when the error has violations: one `FieldViolation` per violation (see <<mapping>>). It keeps the
  first violations that fit in about 3 KiB, whole ones only, so that the trailer stays within a client's default
  8 KiB metadata limit.
* `RetryInfo`, when the call was rejected by the concurrency limit: `retry_delay` 1 s.

The description is the formatted message, in the caller's `accept-language` locale, only when
`synapse.errors.include-detail` is `true` (default `false`, in every environment; see xref:core.adoc#errors[Errors]).
Otherwise it is empty. Stack traces, exception class names and internal messages never appear.

The status comes from the error's category:

[cols="2,2",options="header"]
|===
|Category |Status
|`INVALID_INPUT` |`INVALID_ARGUMENT`
|`UNAUTHENTICATED` |`UNAUTHENTICATED`
|`FORBIDDEN` |`PERMISSION_DENIED`
|`NOT_FOUND` |`NOT_FOUND`
|`CONFLICT` |`ABORTED` (the code `ALREADY_EXISTS`: `ALREADY_EXISTS`)
|`PRECONDITION_FAILED` |`FAILED_PRECONDITION`
|`RATE_LIMITED` |`RESOURCE_EXHAUSTED`
|`UNAVAILABLE` |`UNAVAILABLE`
|`TIMEOUT` |`DEADLINE_EXCEEDED`
|`INTERNAL` |`INTERNAL`
|===

Core's `STALE_VERSION` is therefore `ABORTED`, unless the request sent an `etag`: then it is answered
`PRECONDITION_FAILED` (`FAILED_PRECONDITION`), as REST answers a stale `If-Match` 412 (see <<versions>>).

Override the status of any code, for every operation or for one, with the code in brackets and a `Status.Code` name:

[source,properties]
----
synapse.api.grpc.errors.status.[BOOK_NOT_FOUND]=FAILED_PRECONDITION
synapse.api.grpc.operations.get-book.errors.status.[BOOK_NOT_FOUND]=OUT_OF_RANGE
----

The first that applies wins: the operation's override, the global override, the fixed status of a built-in code
(`ALREADY_EXISTS`, and `METHOD_NOT_FOUND`), the category's status. An override of `OK` fails startup with
`<key>.[<code>] is OK, which is not an error status.`

[#not-found]
=== Not found

An empty `Optional` output (or `null` for an `Optional` output) is `NOT_FOUND` with the code `NOT_FOUND`, or the code
given to `.notFound(code)`. Over gRPC the error gets no message arguments, because a request has no path variables to
fill them from (REST fills `+{0}+` from the route's path variables; see xref:rest.adoc#responses[REST responses]):

* When the declared code's template has placeholders (`+Book {0} was not found+`), or is not a valid `MessageFormat`
  pattern, the description is `NOT_FOUND`'s message (`The resource was not found`, or its localized `MessageSource`
  entry) instead of the template unfilled. The reason in `ErrorInfo`, and the status with its overrides, stay those of
  the declared code.
* A template without placeholders keeps its own text.
* The decision is made on the template only. A `MessageSource` entry for the code takes the same arguments as the
  code's template: a template with placeholders whose localized entry has none still gets `NOT_FOUND`'s message, and a
  template without placeholders whose entry has some shows that entry as written.

To give a gRPC caller a specific message, give `.notFound` a code whose template has no placeholders, or throw the
`SynapseException` with its arguments from the operation.

=== Calls that never reach an operation

[cols="2,2,4",options="header"]
|===
|Case |Status |Details
|Request bytes that aren't a valid message |`INVALID_ARGUMENT` |`ErrorInfo` with `MALFORMED_REQUEST`, and the
correlation id.
|A method no service declares |`UNIMPLEMENTED` |`ErrorInfo` with `METHOD_NOT_FOUND` (`GrpcErrors`), and the correlation
id in the trailers and in `ErrorInfo`.
|A message over `spring.grpc.server.inbound.message.max-size` |`RESOURCE_EXHAUSTED` |None: grpc-java's own status.
|Metadata over `spring.grpc.server.inbound.metadata.max-size` |The client's own failure |None (see below).
|The concurrency limit reached |`UNAVAILABLE` |`ErrorInfo` with `UNAVAILABLE`, and `RetryInfo` of 1 s.
|===

* *Unknown methods* are answered by Synapse's fallback handler registry (the `ServerBuilderCustomizer` bean
  `synapseGrpcFallbackHandlers`). grpc-java runs a fallback method without the server's interceptors, so neither the
  edge nor tracing sees these calls: the registry accepts the caller's correlation id (validated as in
  xref:core.adoc#correlation-id[Correlation id]) or generates one itself, and never reads the request.
* *An oversized message* is rejected by grpc-java, which checks the size only once the call has asked for its message.
  The call therefore reaches the interceptors (`interceptCall`, then `onCancel`), but no message is delivered: the
  operation is not invoked, no exception handler runs, the call's concurrency permit is released, and Synapse logs
  nothing. The client gets `RESOURCE_EXHAUSTED` with grpc-java's description and no `ErrorInfo`.
* *Oversized metadata.* The server advertises its metadata limit in its HTTP/2 settings
  (`SETTINGS_MAX_HEADER_LIST_SIZE`, 16384 bytes by default), so a grpc-java client refuses to send larger metadata
  and fails the call itself, before the server sees it.

=== Exception handlers

Synapse's `GrpcExceptionHandler` (`synapseGrpcExceptionHandler`) is ordered last, so your handlers, `@GrpcAdvice`
classes and Spring Security's handler answer first; Spring gRPC uses the first answer. Synapse's handler always
answers:

* a `StatusException` or `StatusRuntimeException` passes through unchanged (an escape hatch's explicit choice); the
  edge still adds the correlation id to the trailers;
* a `SynapseException` is written as above;
* anything else is `INTERNAL`, logged once at ERROR with its stack trace on `io.americanexpress.synapse.api.grpc`, with
  the correlation id.

IMPORTANT: A `@GrpcAdvice` class and its `@GrpcExceptionHandler` methods must be `public`. Spring gRPC invokes them
without making them accessible; otherwise the call is answered `INTERNAL`, with no `ErrorInfo`.

Logging: failures of operations are logged by the pipeline (see xref:core.adoc#logging[Logging]). A call rejected
before an operation runs (a malformed request, binding violations, a missing required or a weak `etag`, the
concurrency limit, an unknown method) is logged at DEBUG at most.

[#correlation-id]
== Correlation id and context

The edge opens the Synapse `RequestContext` around every listener callback of a call, inside the span of Boot's
server observation, so the correlation id and attributes reach the MDC, the logs, `@Async` and virtual threads and
outbound calls. The context is closed on the callback's thread when the callback returns or throws, so no context or
MDC entry is left on a reused executor thread.

* *Correlation id:* read from the metadata key `synapse.correlation.header` in lower case (`x-correlation-id`), first
  value, then validated and generated as described in xref:core.adoc#correlation-id[Correlation id]. It is echoed in
  the response headers when they are sent, or in the trailers when the call ends without headers (as an error
  usually does), always as the resolved id. It also tags the server observation as `correlation.id`.
* *Context attributes:* each one maps a metadata key to an attribute name:
+
[source,properties]
----
synapse.api.grpc.context.metadata.tenant=x-tenant
synapse.api.grpc.context.metadata.channel=x-channel
----
+
Keys must be lower case, ASCII (not ending in `-bin`) and valid metadata keys; otherwise startup fails. Attributes are
read in this order, from the first value of the key, so when there are more than the context limits allow
(`synapse.context.inbound.max-entries`, `.max-size`), the last ones are dropped. An empty value counts as absent.
* *Locale:* from the first language range of `accept-language` (by weight), only when present.

Synapse adds `correlationId` and the attribute names to Boot's baggage remote fields and correlation (MDC) fields, as
for REST. So each attribute is a field of every log line in the call. A name that collides with another field would
overwrite it, or be overwritten (the MDC holds one value per name), or make Boot drop the lines that carry both (a
key-value of the same name on Logback, or a dotted name that ECS nests). Startup fails when an attribute's name is one
of these, or starts with one followed by a dot:

* a top-level field Boot's ECS log format writes itself (`@timestamp`, `log`, `process`, `service`, `message`,
  `error`, `tags` or `ecs`), such as `log.level`;
* a log field Synapse or Boot's tracing sets (`correlationId`, `traceId`, `spanId`, `operation`, `errorCode` or
  `errorCategory`), such as `traceId.x`;
* another attribute's name, such as `tenant` and `tenant.region`.

The same name here and under `synapse.api.rest.context.headers` is one attribute. See
xref:logging-log4j2.adoc#ecs[ECS JSON by default] for why.

=== Baggage and trust

A trusted caller (the default, `synapse.context.inbound.trusted=true`) can also send the correlation id and the
attributes as W3C `baggage` entries named `correlationId` and after each attribute, or in metadata keys of those names
when they are remote fields. The edge removes these Synapse fields from `baggage` before tracing reads it; they are only
candidates, used when the mapped key is absent, and are validated like metadata values. Other baggage entries and
remote fields pass through.

A public-facing service sets `synapse.context.inbound.trusted=false`. Then the edge hides from Boot's observation
interceptor and everything after it:

* the trace keys, so each call starts a new trace: W3C Trace Context (`traceparent`, `tracestate`) and B3 (`b3`,
  `x-b3-traceid`, `x-b3-spanid`, `x-b3-parentspanid`, `x-b3-sampled`, `x-b3-flags`) only;
* `baggage` and the key of every remote baggage field (`management.tracing.baggage.remote-fields`);
* and core drops the inbound context attributes. The correlation metadata is still accepted.

WARNING: The masking works on the metadata that Boot's observation interceptor reads. A tracer that reads metadata
before the interceptors, such as a `ServerStreamTracer` (grpc-opentelemetry added with a `ServerBuilderCustomizer`),
is not covered by `trusted=false`. The same holds for the OpenTelemetry Java agent, which instruments grpc-java
itself: under the agent, `trusted=false` does not restart the trace, and dropping the caller's baggage is not
verified. A Synapse agent extension that closes this gap is planned; until then, see
xref:opentelemetry-agent.adoc#untrusted[the agent page] for the setting that restarts the trace.

Never base a security decision on an attribute or on baggage; callers control them.

== Deadlines

The call's gRPC deadline becomes the request deadline, capped by `synapse.api.grpc.deadline.max` (30s). A call
without a gRPC deadline gets `synapse.api.grpc.deadline.default` (10s), so every call has a deadline. The default must
be positive and not above the maximum; otherwise startup fails. The cap applies only to the request context: the
call's own gRPC deadline stays as the caller set it. The pipeline fails a call whose deadline has passed with
`DEADLINE_EXCEEDED` before `execute`; a running operation is not interrupted.

== Limits

[cols="2,1,4",options="header"]
|===
|Limit |Default |Property
|Inbound message |4 MB |Boot's `spring.grpc.server.inbound.message.max-size`
|Inbound metadata |16 KB |Boot's `spring.grpc.server.inbound.metadata.max-size`, which Synapse defaults to 16KB (Boot's
own default is 8 KB) at lowest precedence, so your value wins
|Concurrent calls |200 |`synapse.api.grpc.max-concurrent-calls` (at least 1)
|===

*Concurrency.* With virtual threads, the server's executor no longer limits how much work runs at once, so the edge
caps it. A call that finds the limit reached is closed at once with `UNAVAILABLE` and `RetryInfo` of 1 s, and nothing
behind Synapse's context interceptor runs; it never waits. Calls to `grpc.health.v1.Health` and both server
reflection services are never counted, so health checks are answered under full load.

A call holds its permit until it completes or is cancelled. grpc-java delivers the cancellation only after the
callback that runs the operation returns, so a cancelled call, or one whose deadline expired, holds its permit until
its handler returns. An operation that blocks should watch the call's gRPC `Context` cancellation or its
`RequestContext` deadline.

== Threads

When `spring.threads.virtual.enabled=true`, Synapse gives Boot's server a `GrpcServerExecutorProvider` that runs each
call on a new virtual thread named `grpc-<n>`. It is closed with the context, after the gRPC server has stopped: it
waits for calls still running for at most `spring.grpc.server.shutdown.grace-period`, then interrupts them. Define a
`GrpcServerExecutorProvider` bean to replace it.

[#edge-interceptors]
== Edge interceptors

The edge is two global server interceptors around Boot's. Replace one by defining a bean with its name.

[cols="2,1,4",options="header"]
|===
|Bean |Order |Does
|`synapseGrpcEdgeInterceptor` |`HIGHEST_PRECEDENCE` |Hides or strips propagation metadata before tracing reads it,
and echoes the correlation id.
|Boot's observation interceptor |`0` |The server observation and its span.
|Boot's exception handling interceptor |`1` |Asks the `GrpcExceptionHandler` beans for a failure's status.
|`synapseGrpcContextInterceptor` |`100` |Opens the request context (correlation id, attributes, locale, deadline)
and caps concurrent calls.
|===

The other beans (`grpcDeadlinePolicy`, `grpcConcurrencyLimit`, `grpcErrorStatuses`, `grpcStatusWriter`,
`synapseGrpcExceptionHandler`, `synapseGrpcServiceCompiler`, `synapseGrpcBindingsCompiler`,
`synapseGrpcExposureInventory`, the virtual-thread executor provider, the `synapseGrpcFallbackHandlers` customizer,
the `synapseGrpcServletCheck` startup check, and the `synapseGrpcReflectionAotCheck` build-time switch) back off when
you define your own.

== Server reflection

Server reflection publishes the whole API to any caller, so it is off by default: Synapse sets Boot's
`spring.grpc.server.reflection.enabled` to `false` at lowest precedence, in every environment. An environment file
turns it on, for example for `grpcurl` in local runs (see xref:environments.adoc#safe-defaults[Safe defaults]):

[source,yaml]
----
# application-local.yaml
spring:
  grpc:
    server:
      reflection:
        enabled: true
----

The key decides whether Boot defines its reflection service bean, so under AOT it is a build-time switch (see
xref:environments.adoc#aot-switches[AOT and native images] for the rule and its message). Its value is read as Boot
reads it: on when unset or `true`, off for any other value. It is compared only when Boot could have defined the
bean: `grpc-services` is on the class path and the application has a service of its own.

== Health

Health checks are Boot's: its `grpc.health.v1.Health` service, configured under `spring.grpc.server.health.*`.
Synapse adds nothing to it, and never counts its calls against the concurrency limit.

[#shutdown]
== Shutdown

Boot's gRPC server stops first: its lifecycle has the highest phase, above Synapse's `INBOUND` and `DRAIN` phases. It
refuses new calls (`UNAVAILABLE`) and waits for the calls in flight for at most
`spring.grpc.server.shutdown.grace-period` (30s, Boot's default), then cancels the rest. Its stop is synchronous, so
this wait is not bounded by `spring.lifecycle.timeout-per-shutdown-phase`; count it as its own term in the Kubernetes
formula (see xref:core.adoc#shutdown[Shutdown]). Then the pipeline drains the operations still running.

== Exposure inventory

When the gRPC server starts, the plugin logs every method it binds, one INFO line each on
`io.americanexpress.synapse.api.grpc`:

----
Synapse gRPC exposes synapse.samples.inventory.v1.InventoryService/GetItem -> get-item on port 9090
----

A server without a port (in process) is reported as `in process`. Hand-written services are not listed.

[#escape-hatch]
== Escape hatch

A hand-written service (a `*ImplBase` subclass declared as a bean) that injects operations is the escape hatch for
what bindings can't express, streaming methods included. The operation call runs through the pipeline, and the
service gets the same edge: correlation id and context, deadline, concurrency limit and error details.

[source,java]
----
@Component
class WatchService extends WatchServiceGrpc.WatchServiceImplBase {

    private final GetBookOperation getBook;

    WatchService(GetBookOperation getBook) {
        this.getBook = getBook;
    }

    @Override
    public void watchBook(WatchBookRequest request, StreamObserver<BookEvent> events) {
        ...
    }
}
----

* An exception the service throws goes through the exception handlers above: a `SynapseException` gets the Synapse
  error details, a `StatusException` or `StatusRuntimeException` passes through, anything else is `INTERNAL`. So does
  an exception passed to `responseObserver.onError(...)`, except a status exception, which reaches the caller as it
  is, with the correlation id added. This holds when the service completes the call from a thread of its own (a
  future's callback, a streaming producer): the error details carry the call's correlation id and locale.
* The service maps messages itself; no field mapping, violation paths or not-found handling apply.

== Native image and AOT

The plugin registers lambda hints for the method references in bindings. Synapse reads a reference such as
`CreateBookRequest::channel` through its serialized form, which a native image allows only for lambda classes with
metadata. The hint is registered for the class that declares the `@Bean` method of each `GrpcBindings` bean, covering
every method reference created in that class. So:

* write the method references in the class that declares the `@Bean` method, not in a helper class it calls;
* declare the `@Bean` method's return type as `GrpcBindings`. A wider type (for example `BindableService`), or a
  `GrpcBindings` bean not created by a `@Bean` factory method, gets no lambda hints. In the same way, an operation bean
  declared with a wider type than its class (`ServiceOperation<?, ?>`) gets no hints for its input and output types,
  which core registers from the bean's declared type. The REST plugin has the same limitation.

The plugin needs no other hints: it never instantiates generated message classes, and the records it maps are the
operations' inputs and outputs, which core registers. Spring's AOT processing of a gRPC service is tested on the JVM.
A native image is not verified yet: `grpc-netty`, protobuf's runtime reflection on the descriptors, reflection on the
mapped records and enums, and the lambdas' `writeReplace` method. The native build of the reference application, in
P4, checks them.

== Configuration

The gRPC properties are `synapse.api.grpc.*`; all are in the
xref:reference/configuration-properties.adoc[property reference]: `context.metadata.<attribute>`,
`deadline.default` and `.max`, `max-concurrent-calls`, `errors.status.[CODE]` and
`operations.<name>.errors.status.[CODE]`. The plugin also reads core's `synapse.correlation.*`,
`synapse.context.inbound.*`, `synapse.errors.*` and `synapse.paging.*` (see <<paging>>), and sets defaults for two of
Boot's `spring.grpc.server.*` keys (`inbound.metadata.max-size`, `reflection.enabled`).
