= Samples

The repository's `samples/` directory holds runnable Synapse 2 services. They are never published; each one has a
README with the commands to run it and the output they print. Every sample inherits
xref:parent.adoc[`synapse-parent`], as a consumer's project does. Read them in the table's order: each one adds to the
one before. The table follows
https://github.com/americanexpress/synapse/blob/main/samples/README.md[`samples/README.md`], with links into these
pages.

:samples: https://github.com/americanexpress/synapse/blob/main/samples

== Building a sample

Build and test one through its bootable module, from the repository root. A sample made of modules is built through
the module that starts the service, which pulls in the others (`-pl samples/grpc-inventory` alone would build only
its aggregator pom). `-am` builds and tests the Synapse modules the sample depends on first. multi-store and the
reference bookstore need Docker, for their databases and their Testcontainers integration tests:

[source,bash]
----
./mvnw -pl samples/hello-rest -am verify
./mvnw -pl samples/grpc-inventory/service-inventory -am verify
----

The samples inherit `synapse-parent`, which has no formatter or license check, so the repository root formats their
code (Spotless) and checks their license headers, as root-only executions. A build with `-pl samples/<name> -am`
includes the root, because `-am` adds the parents of the modules the sample depends on, so it formats and checks the
samples too (CI only checks). `./mvnw -N process-sources` formats them without a build. A copy of a sample outside the
repository has neither until you add your own.

Spring AOT processing is opt-in (`-Paot`, `synapse-parent`'s `aot` profile; see
xref:parent.adoc#_build_environment[Build environment]), and only the reference bookstore uses it:

[source,bash]
----
./mvnw -Paot -pl samples/reference-bookstore/service-bookstore -am verify
----

The other samples have no build environment file (`application-build.yaml`), on purpose: they show a service that
needs none. So `-Paot` fails in them, with `The environment 'build' has no file in the service`, and a build with
`-Paot` from the repository root fails too.

== What every sample has

* `application.yaml` with `spring.profiles.active: ${ENV}`, `application-local.yaml` with the local conveniences, and
  `spring-boot.run.profiles=local` in the bootable module's pom (see xref:environments.adoc[Environments]).
* `src/test/resources/application-test.yaml`: the tests run as `test`. The exceptions prove an environment's own
  file: rest-books' `BooksLocalEnvironmentIT` runs as `local` (its `application-local.yaml` turns the OpenAPI document
  on), and the reference bookstore's tests that start the packaged jar run it as `dev` (the scenarios, the agent),
  `build` (the training run's start) or `local` (to show the build-time switch failure).
* Tests at every level, and a one-line `ArchitectureTest` (see xref:testing.adoc[Testing]).
* No later-phase features: no clients, Kafka, GraphQL, functions, security or scheduling.
